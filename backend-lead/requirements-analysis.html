The senior-lead bar

A mid-level submission makes the endpoints work. A senior submission states the invariants first, enforces each one at more than one layer, names every assumption it had to invent, and resists building anything the brief did not ask for. Judgment is the deliverable. The code is evidence for it.

Invariants and where each is enforced

Six properties the wallet must hold. Each gets a structural guard in the database, a behavioural guard in the service, and a test that would fail if either were removed. Write these into DECISIONS.md verbatim.

InvariantDatabase layerService layerTest that proves it
I1 · A completed deposit credits exactly once UNIQUE (psp_ref) on funding transactions. Lock the funding row with FOR UPDATE, then apply the state guard. A second delivery waits, sees Completed, and returns an idempotent 200 without writing. Sequential duplicate; N concurrent duplicates via Promise.all. Assert one ledger row, balance equals amount.
I2 · Balance never goes negative CHECK (balance >= 0) on wallets. Lock the wallet row, compare with BigNumber, debit in the same transaction. Loser gets 422, not a partial write. Balance 100, ten concurrent wagers of 15. Exactly six succeed, balance is 10.
I3 · Ledger reconstructs balance Append-only wallet_txs with signed amount and balance_after. No UPDATE or DELETE path exists in code. Every balance change and its ledger row are written in one transaction. Nothing touches balance outside that path. After a mixed scenario, SUM(amount) over the ledger equals wallets.balance, and the last balance_after matches.
I4 · State transitions are explicit Status stored as an enum with three values. One transition(tx, to) function owns the allowed edges. Repeat of the applied outcome is a no-op; a conflicting outcome is a 409. Callback failed after Completed is rejected and changes nothing.
I5 · Withdrawal only when turnover is met turnover_required and turnover_accrued columns on wallets, both non-negative. Under the wallet lock: if accrued < required, return 422 with the outstanding figure. Deposit completion adds to required; each wager adds to accrued. Blocked with the right outstanding amount, then unblocked after wagers reach the threshold.
I6 · Money never touches a JS number DECIMAL(36,18) everywhere; pg returns strings. Zod validates amounts as decimal strings with at most 18 fractional digits. All arithmetic via lib/money.ts. Pre-submission grep for parseFloat, Number(, +amount in src/ returns nothing.

Rulings on what the brief leaves open

The root readme says gaps are deliberate and that how you frame a missing constraint is part of what is read. Decide these before writing code, record each in DECISIONS.md the moment it is applied.

QuestionRulingWhy this and not the alternative
Callback amount differs from deposit amount Credit the settled amount from the callback. Persist both amount and settled_amount, set amount_mismatch = true, and log at warn level for reconciliation. The callback is what the PSP says actually moved. Crediting the requested amount invents money or hides a shortfall. Parking the transaction in a review state is the other defensible answer; it costs a fourth state and an approval path the brief said not to build. Name it as the production choice in next steps.
Unknown pspRef Persist the raw callback in a psp_callbacks inbox table with outcome orphan, respond 404. Nothing to lock, nothing to credit. Storing the raw payload means a late deposit row or a support case can still be matched. In production many PSPs retry on non-2xx forever, so a 200 acknowledgement is the likely real answer; say so.
Repeat callback with the same outcome 200, idempotent no-op, echo the current state. Retries must be safe to acknowledge. Returning 409 would cause retry storms.
Callback conflicting with a terminal state 409 invalid_transition, no write, inbox row records the rejection. Silently applying it is the failure the brief names. A loud reject is what the state machine is for.
Withdrawal larger than balance 422 insufficient_balance, checked after the turnover gate under the same lock. The brief only mentions the turnover check, but a wallet that never loses money cannot let a withdrawal overdraw. Turnover first because it is the anti-abuse control and its 422 body is specified.
Does a withdrawal reset turnover? No. Required and accrued are lifetime counters; outstanding is max(required − accrued, 0). Simplest model that satisfies the rule as written. Real platforms often reset on withdrawal or per deposit; flag as an open product question.
turnoverMultiplier of 0 Allowed. Adds nothing to required turnover. The brief says integer ≥ 0. Useful for the test scenario too.
Failed deposit and turnover Adds no requirement. Only completion changes wallet state. No money arrived, so nothing to lock against.
Precision of amount Regex ^\d+(\.\d{1,18})?$, must be > 0. More than 18 decimals is a 400. Anything the column cannot hold exactly should be rejected at the edge, not rounded silently.
Currency Single implicit currency. Out of scope, named in next steps. Adding a currency column without conversion rules is theatre.

Locking strategy and schema

The one design decision that shapes everything else. Pick it, write down why, and name the alternatives you rejected.

Pessimistic row locks, one transaction per money movement

Every service method opens a Sequelize transaction, locks the rows it will change with lock: t.LOCK.UPDATE, checks, writes, commits. Postgres serialises concurrent callers on the locked row, so the second delivery or the second wager observes the first one's committed result.

Lock order is fixed: funding transaction first, then wallet. Wagers and withdrawals lock only the wallet. No path locks in the other order, so no deadlock is possible.

Rejected: SERIALIZABLE with retry loops adds a retry layer a junior will get wrong and gives no benefit at this scale. Optimistic versioning makes hot wallets retry-storm under load and moves the correctness burden to every caller. Both are worth one paragraph in DECISIONS.md.

Test harness detail: Sequelize's default pool is 5 connections. With ten concurrent requests, five queue on the pool before they ever reach the lock. Raise pool.max to at least the concurrency you test with in the test config, so the race is real and the lock is what serialises it.

Schema additions, three migrations

TableKey columns
funding_txsid, wallet_id, kind (deposit | withdrawal), status (Pending | Completed | Failed), amount, settled_amount, amount_mismatch, psp_ref unique, turnover_multiplier, created_at, updated_at
wallet_txsid, wallet_id, funding_tx_id nullable, kind (deposit_credit | wager_debit | withdrawal_debit), amount signed, balance_after, created_at. No updated_at: the row is never updated.
psp_callbacksid, psp_ref, payload jsonb, outcome (applied | duplicate | orphan | rejected), received_at. Raw inbox; also the seed for Part B's replay harness.
wallets (alter)turnover_required, turnover_accrued, CHECK (balance >= 0)

Materialised balance plus append-only ledger, rather than ledger-only, keeps every read a single row and keeps the invariant provable with one SUM. balance_after on each ledger row makes any drift locatable to the exact entry.

Funding transaction state machine

                      callback completed
  POST /deposits ──▶ Pending ─────────────────▶ Completed   (credit wallet, add amount × multiplier
                        │                                    to turnover_required, ledger row)
                        │ callback failed
                        └───────────────────▶ Failed        (no balance change)

  Terminal states accept a repeat of the same outcome as a 200 no-op
  and reject a different outcome with 409. Nothing leaves a terminal state.

  POST /withdrawals ─▶ Pending   (wallet debited immediately; approval is out of scope)

Common way this goes wrong

A concurrency test that awaits requests in a loop is a sequential test with a misleading name. Build the array of promises first, then await them together. Check the pool size note above, and assert exact counts of successes and failures rather than "at least one".

Part B · DESIGN-PSP.md

45 min · 3:15 to 4:00

One page and one sketch. The question is how a junior ships PSP number fifty in a day without being able to break the wallet. Answer it in that order: what they write, what stops them breaking things, how they prove it works.

Structure to describe

  • Adapter interface. verify(raw) → payload and normalize(payload) → PspEvent. Adapters never import wallet code.
  • Canonical event. { provider, pspRef, providerEventId, status: pending | completed | failed, amount in major units as string, currency, receivedAt, raw }. The A2 service becomes applyPspEvent(event) and is provider-blind.
  • Pipeline. POST /psp/:provider/callbacks → registry lookup → persist raw inbox row → verify → normalize → apply. Verification and normalization live at the edge; the core sees only canonical events.
  • Quirks die at the edge. Minor units become a unitScale config. Status vocabularies become a statusMap. Out-of-order success-before-pending is absorbed because the core state machine is monotonic and ignores regressions.
  • Config over code. A declarative adapter (HMAC header name, secret ref, JSON paths, unit scale, status map, ack policy) covers most providers with a config file and zero code. Custom classes only for the strange ones.

Safety and testing to describe

  • Contract test suite. Every adapter must pass one shared suite fed by a fixtures directory: valid, tampered signature, duplicate, minor units, out-of-order, unknown ref. CI runs it with no network.
  • Recorded fixtures. Captured from the provider sandbox and from the production inbox table, redacted. The inbox from Part A is the replay source.
  • Sandbox smoke nightly and non-blocking; the provider's uptime is not your CI's problem.
  • Shadow mode. New adapters roll out in observe mode: verify, normalize, log, do not apply. Flip to live per provider by config.
  • Guardrails. Code owners on the core wallet path, an adapter template generator, and a one-day checklist: morning is fixtures, config and adapter; afternoon is contract suite green, shadow mode in staging, PR.

The sketch is the pipeline above as a single flow diagram with a bold line between "adapter" and "core". That line is the whole argument.
